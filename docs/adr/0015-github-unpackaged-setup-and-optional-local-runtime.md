# ADR 0015: GitHub Unpackaged Distribution and Optional Local Inference Component

- Status: Accepted
- Date: 2026-08-13
- Supersedes the previous packaged/MSIX distribution decision and revises the data root, notification registration, and local component deployment location

## Context

PicForLater is distributed to Windows users through GitHub Releases and does not depend on the Microsoft Store.
Cloud-only users should not have to download ONNX Runtime, GenAI, and CUDA/DirectML, so local inference is split into an optional component. The first release does not require code signing; the SmartScreen prompt for unsigned versions must be disclosed accurately.

## Decision

1. The application uses truly unpackaged WinUI 3, is built with `WindowsPackageType=None`, and launches from a regular EXE. It does not generate an application MSIX or assume package identity.
2. Each GitHub Release provides online/offline Setup, Windows App Runtime ZIP, and VC redist for x64 and ARM64, plus a signed manifest, detached signature, and ZIP for the optional local component. No checksum sidecar is uploaded. Users obtain application updates manually; no background auto-updater is added. The README and Release notes must disclose the unsigned status and what to expect from SmartScreen.
   Official Setup is generated by GitHub Actions from artifacts published in the same Release. CI and release workflows use only official GitHub Actions, pinned to full commit SHAs.
3. The data root is fixed at `%LocalAppData%\PicForLater` and holds the database, originals, cache, staging, models, settings, and optional components. Upgrade installations and ordinary uninstalls preserve data. Core and Infrastructure receive only injected absolute root paths. Preferences use storage available to unpackaged applications. API keys go only into secure credential storage for the current Windows user; they must never fall back to plaintext JSON, the registry, or the database.
4. Ordinary notifications and scheduled reminders both use the unpackaged-compatible `ToastNotificationManagerCompat` path. Do not mix in `AppNotificationManager` or `ToastNotificationManager.CreateToastNotifier()`, which requires package identity. The SQLite outbox is the source of truth, and the application does not elevate privileges. Normal shutdown only unsubscribes from activation events; the main EXE calls `Uninstall()` only when launched by Setup with `--uninstall-notifications`.
5. The core uses framework-dependent deployment with .NET and Windows App SDK. Setup reuses compatible `Microsoft.NETCore.App`, `Microsoft.AspNetCore.App` 10.0, Windows App Runtime, and VC redist installations, installing only runtimes that are missing or below minimum requirements; end users do not need the .NET SDK.
   Online Setup obtains the architecture-matched Windows App Runtime ZIP and VC redist from the same Release, and obtains .NET/.NET Core EXEs from official Microsoft sources. Offline Setup includes all prerequisite runtimes and requires no network access.
   A manifest pins the payloads. The minimum .NET version is derived from the published runtimeconfig, and the ASP.NET Core requirement on the base .NET version is checked. Prerequisite payloads are checked for length and SHA-256; installer EXEs also undergo Authenticode verification. MSIX files inside the Windows App Runtime ZIP are separately verified for Microsoft's signature and package identity, then registered for the current user using `Add-AppxPackage` for the framework, Main, Singleton, and DDLM packages. The application itself is still not registered as an MSIX.
6. Online payloads use the system .NET networking library. If Range is supported, download concurrently in 8 segments, display total progress and speed, and allow the download to be stopped; otherwise reuse the single-connection response. Verify the response range and length of each segment. After merging, perform exactly one full SHA-256 check per payload before installation; correct length or Range responses do not replace content validation. Subsequent segments reuse the address after GitHub redirection has completed. On failure or cancellation, delete temporary segments; do not retain partial download state.
7. Setup installs per-user with `PrivilegesRequired=lowest` to `%LocalAppData%\Programs\PicForLater` and does not elevate to overwrite the installation. Installing .NET, ASP.NET Core, or VC redist requests administrator authorization as required; VC redist is a machine-level installation, while Windows App Runtime is registered for the current user.
   Copy the application only after prerequisites are ready, then create Start menu shortcuts and an optional desktop shortcut. An upgrade reuses the directory and task selection. Uninstall removes the application, shortcuts, notification registration, and uninstall entry while preserving user data.
   After exit code 3010, recheck dependencies; continue if they are ready, otherwise require a restart. Exit code 1641 means a restart has already begun, so stop installation immediately and do not clear the system's pending-restart record. Keep the window responsive while waiting for child processes and show the component and elapsed time; disable navigation and cancellation during runtime installation. Temporary Setup logs record steps, elapsed time, and exit codes.
8. ONNX Runtime, GenAI, CUDA/DirectML, PP-OCR/Qwen implementations, and the local worker are removed from the core App build/publish graph. The core retains only the versioned pipeline client, remote Providers, SQLite jobs, and lightweight Windows OCR/image cleanup. The component is installed at `%LocalAppData%\PicForLater\components\local-inference\<arch>\<version>`:
   - The outer release manifest uses an RSA-PSS/SHA-256 detached signature. The App accepts only the original JSON bytes that validate against the embedded public key. Component downloads remain disabled until the trust root and stable Release source are confirmed.
   - The manifest pins the component ID, architecture, protocol, compressed/decompressed sizes, and SHA-256 hashes for the ZIP and `component.json`. Each download hop is restricted to official GitHub Release/release-assets domains and sends no cookies.
   - After extraction, revalidate paths, entry count, reparse points, per-file hashes, and files not listed in the manifest. Only after download and revalidation may the worker maintenance phase begin: wait for the current operation to finish, stop the worker, and atomically switch `active.json` under a maintenance lease. File hashes alone do not prove release origin; signature verification failure must not fall back to accepting an unsigned ZIP.
   - The client starts the worker only from a validated and activated version directory. If the component is missing, its architecture/protocol does not match, or validation fails, local mode is explicitly unavailable; it does not silently switch to the remote API.
9. A Release publish must include the main EXE, `PicForLater.App.pri`, and all XBF files from the same WinUI build. Build scripts validate required resources and reject prohibited local-inference files, preventing incomplete layouts that install but cannot start.
10. Register a stable instance key through `AppInstance` before XAML initialization. Subsequent launches in the same test or production channel redirect activation to the existing instance and exit; the main process restores its window and requests foreground without creating a second Application/MainWindow. Unregister the instance key when the window closes. The `--uninstall-notifications` maintenance entry point does not participate in redirection.

## Migration and Compatibility

Retain the database schema, relative paths, jobs, privacy boundaries, pipeline protocol, and the worker's 45-second idle exit. Deployment migration does not rewrite business layers or expand network behavior.

## Consequences

- Cloud-only users do not need to download local inference resources; local users explicitly enable the feature before installing the components and models for the corresponding architecture.
- The first online installation downloads only missing prerequisites; updates in a compatible environment do not download them again. Offline Setup supports installation without a network connection.
- Setup, the component installer, and application validation assume the installation, update, rollback, integrity, and uninstall responsibilities previously provided by the application MSIX.
- Every unsigned version may trigger SmartScreen, and enterprise policy or Smart App Control may still block it. GitHub hosting, public source code, and signed component manifests do not establish Setup Authenticode identity or SmartScreen publisher reputation.
